## Issue 1: Go scaffold with mow.cli, default help, positionals, and root validation

**Type**: HITL
**Blocked by**: None — can start immediately

### Parent PRD

`Notes/PRD-vrg.md` (revision 6)

### What to build

Bootstrap the greenfield Go project (module, `cmd/vrg` main, package layout for the six modules named in *Module Design*, and pinned dependencies on `github.com/jawher/mow.cli`, Bubble Tea, Bubbles, and Lip Gloss). Build a runnable `vrg` executable whose CLI module uses `mow.cli` for command-line parsing and generated usage/help, delivering the first end-to-end invocation path: help, validated `vrg pattern [root]`, or a usage error.

- **Default and explicit help**: bare `vrg`, `vrg -h`, and `vrg --help` print generated command-line help to stdout and exit 0, with no error diagnostic. These paths do not validate a root, start ripgrep, or initialize the TUI, and work even when ripgrep is unavailable.
- **Help content and ownership**: generated help documents invocation syntax, the required pattern, optional root and its `.` default, and local `-h`/`--help` options. Issue 2 adds the search-flag declarations and their generated help when implementing forwarding. This is command-line help, not the TUI key-binding dialog delivered by Issue 31.
- **Positionals**: first is the pattern, second is the root, root defaults to `.`. Outside help-only paths, missing pattern or more than two positionals is a usage error. A **present but empty** pattern argument is present, not missing: `vrg "" .` parses successfully and retains an empty pattern (forwarding it verbatim in child argv is Issue 2).
- **Local help and option boundaries**: recognize `-h`/`--help` as local options anywhere before `--`; never treat them as search flags. The first `--` ends option parsing; all subsequent tokens are positional, including `-h`, `--help`, and another `--`. Assignment spellings such as `-h=false` and `--help=false` are not help requests. A literal pattern `-` is valid. Unsupported options produce usage errors when no help request is present. Search-flag acceptance, combined-short expansion, cumulative `-u`, and ordered child argv remain Issue 2; that extension must extend the same raw-token preflight scan and shared option declarations established below rather than reject help under its search-flag allow-list.
- **Root validation**: before any TUI starts, accept an existing directory or regular file, including symlinks resolving to either. Reject `-` (stdin), special files, and nonexistent paths. An actual regular file named `-` is addressed as `./-` and accepted.
- **Safe output and errors**: usage errors print a sanitized single-line diagnostic to stderr and exit 2 with no TUI or child. Any additional usage text on error also goes to stderr. Help and diagnostics must obey the PRD's output-safety contract, including substitutions derived from arguments or the executable name. Escape invalid bytes and dangerous controls in offending operands rather than letting library output bypass sanitization. A minimal shared escaper is acceptable here; Issue 6 generalises it.
- **Successful search stub**: for now, a valid search invocation may print a safely escaped representation of the parsed pattern and root and exit 0, enough to prove the slice end-to-end. Distinguish help-only results from successful search parses so the entry point cannot fall through into this stub after printing help. Later issues replace the stub with search and browsing.

#### Integrating `mow.cli`

Pin `github.com/jawher/mow.cli` at `v1.2.0` (the current release). Keep it behind the CLI module's interface: the module's outputs are a help-only result, a parsed search invocation, or a sanitized usage error, exactly as *Module Design → CLI* specifies; callers never see library types. Probing the library shows these defaults conflict with the PRD and must be handled explicitly:

- **Exit ownership**: `cli.App` defaults to `ErrorHandling = flag.ExitOnError`, so `Run` calls `os.Exit` itself (0 for help, 2 for errors) before returning. Set `flag.ContinueOnError` so the CLI module returns a result and the entry point in `cmd/vrg` decides the exit status. Exit ownership and output ownership are separate: `ContinueOnError` changes exit behavior only and does not suppress the library's own writes (see the output-destination bullet).
- **No-argument path**: with a required `PATTERN` argument the library treats an empty argv as `incorrect usage`. Detect the empty argument list in the CLI module and return the help-only result before invoking the library parser.
- **Help placement and precedence**: the library's built-in `-h`/`--help` interception only triggers when help is the *first* token, and option values are filled only after the entire FSM parse succeeds, so `-i --help` or `-ih` without a pattern and `foo bar baz --help` fail with `incorrect usage` before a set help value could ever be observed — a late help request cannot be discovered from parsed option values at all. Resolve local help in an option-aware **preflight over the raw argument tokens**, run before the library parser and before the required-pattern, arity, and root checks: scan argv left to right, stop at the first `--` (tokens after it are positional operands, never help), and treat a token as a help request exactly when it is the literal `-h`, the literal `--help`, or a combined short token containing `h` (recognizing combined help the same way Issue 2 expands combined search flags). Declare `h help` as a local boolean option anyway — generated help must document it, and a fully successful parse can carry a set help value (see the help-only-versus-success bullet). The first help request wins regardless of any other tokens — including invocations that would otherwise be missing-pattern, excess-operand, unsupported-option, or invalid-root usage errors — and yields the help-only result before any search action. Build this preflight as the single ordered raw-token scan over the argv, backed by a shared option-declaration table: Issue 2 extends the same scan and table to record accepted search-flag spellings in encounter order, so they must be designed to grow rather than be replaced. The spec still permits options between and after positionals (`[OPTIONS] PATTERN [OPTIONS] [ROOT] [OPTIONS]`, verified with the probed option set to accept `vrg foo --help /nonexistent` and `vrg foo -i src -s`, and to stop at `--`); on such a fully successful parse with a set local help value the library does invoke `Action`, so the adapter must also check the help value before any root validation or search work — help handling may not assume `Action` is always skipped.
- **Output destination**: the library writes all help and parser diagnostics to an unexported package-level writer initialized from `os.Stderr` at package init; there is no writer injection point, and reassigning the application's `os.Stderr` variable later does not reach the already-initialized library variable. The PRD requires help on stdout and sanitized output everywhere, so the chosen output strategy must cover **every library emission point**: (i) first-token help prints via `PrintLongHelp` inside `Cmd.parse` before returning; (ii) an FSM parse failure writes `Error: …` and invokes `PrintHelp` before returning the error — `ContinueOnError` changes exit behavior only and suppresses neither write; (iii) any explicit help-print call the module itself makes. Two acceptable designs, chosen under the human decision below: (a) contain the emissions by capturing at the file-descriptor level around every library call that can emit — this requires process-wide serialization while the descriptor is swapped (the whole process shares it), concurrent drainage of the capture pipe so a large library write cannot deadlock on pipe capacity, and reliable restoration on all controlled paths; or (b) prevent the emissions — render help from the same declared spec, argument, and option metadata that configures the library (so the two cannot drift) **and** guarantee by construction that no library call can emit: the preflight resolves every help request before `Run` is invoked, and `Run` is not invoked on input the preflight has not already validated against the shared declarations, so the library's first-token-help and parse-failure emission paths are unreachable. A metadata renderer alone is not sufficient; it must be paired with such prevention or containment. Prefer an approach that does not introduce unsynchronized global stderr mutation into a reusable CLI module. Either way, nothing external (argv values, `os.Args[0]`) may reach the output unsanitized; using the fixed name `vrg` for `cli.App` is the simplest way to avoid an executable-name substitution.
- **Diagnostic specificity**: the library's parser reports only the bare string `incorrect usage`, with no offending operand. The CLI module must classify failures itself (missing pattern, too many operands, unsupported option, invalid root) and compose the sanitized single-line diagnostic; do not surface the library string as the user-facing message.
- **Help-only versus success**: distinguish the two help routes explicitly. The library's built-in first-token interception returns `nil` from `Run` without invoking `Action`. A locally declared help option on a fully successful parse is different: `vrg foo --help /nonexistent` parses with the help value set and `Action` **is invoked**, so an `Action` that validates the root or starts search work before checking help would violate the no-side-effects requirement. The preflight's help-only result — produced before the library parser runs — is the authoritative outcome; if a set local help value is ever observed on a successful parse, the adapter must produce the same help-only result before any root validation or search work. Represent the outcome with an explicit result kind rather than inferring it from the returned error.
- **Verified library behaviour and limits**: `--` ends option parsing natively (`vrg -- --help`, `vrg -- -h`, `vrg -- --`, `vrg - .`, and `vrg "" .` all parse as literal positionals) and combined short tokens such as `-ih` expand. But `VarOpt` callbacks do **not** preserve cross-option encounter order: the library collects values per option container during the FSM parse and then fills containers by iterating a map, so for `-i -s -i` a shared callback log receives `i,i,s` or `s,i,i` — never `i,s,i` — combined tokens do not change this, callback order is nondeterministic, and callback values do not identify which short/long alias was supplied. The library also does not limit repetitions (`-uuu` parses) and accepts `=`-assignment forms for boolean-valued options (`--ignore-case=false` and `-i=false` parse, delivering `false` to the value). Consequently, ordered forwarding, cumulative `-u` counting, exact no-argument spellings, and generated flag help in Issue 2 must be built on the ordered preflight scan and the shared option-declaration table — the same declarations configure the library, drive the scan's validation, and render help, so no independently drifting allow-list exists — while `mow.cli` remains responsible for the declared syntax and parsing. If custom boolean `VarOpt` values are retained for any option, their value type must implement `IsBoolFlag() bool`; implementing `flag.Value` alone makes them argument-taking options.

See PRD *Implementation Decisions → Invocation and child arguments*, *Outcome and exit-status contract*, *Module Design → CLI*, and *Testing Decisions → CLI*.

**Human decision required**: confirm module path, package layout (e.g. `internal/cli`, `internal/searchindex`, …), Go version, pinned `mow.cli` / Bubble Tea / Bubbles / Lip Gloss versions, and which output strategy — file-descriptor capture with its serialization, drainage, and restoration obligations, or metadata rendering paired with guaranteed prevention of every native emission — satisfies the stdout-and-sanitization contract across every library emission point (first-token help, parse-failure output, and any explicit help print), before merging. The choice to use `github.com/jawher/mow.cli` and the help behavior are already requirements, not open product decisions.

### How to verify

- **Manual**:
  1. `go build ./...` succeeds; `go test ./...` passes; `go.mod` pins `github.com/jawher/mow.cli v1.2.0` and `go mod verify` is clean. Build a runnable binary with `go build -o ./vrg ./cmd/vrg` and use that binary for the checks below.
  2. Run `./vrg`, `./vrg -h`, and `./vrg --help`, capturing stdout, stderr, and exit status separately. Each prints usage/help to stdout, leaves stderr empty, and exits 0 without a search stub or TUI. Repeat with ripgrep unavailable on `PATH`.
  3. `./vrg foo --help /nonexistent`, `./vrg -h foo bar baz`, and `./vrg foo bar baz --help` show help and exit 0, demonstrating help before root validation and arity checks, help accepted after the pattern, and later-token help overriding excess operands. `./vrg -i --help`, `./vrg -ih`, and `./vrg --unsupported --help` also show help and exit 0 — a help request anywhere before `--` wins over the missing-pattern and unsupported-option checks — while the same invocations without a help spelling remain usage errors with exit 2.
  4. `./vrg foo` prints the stub success line with root `.` and exits 0.
  5. `./vrg --` (missing pattern) and `./vrg a b c` (excess operands) produce specific stderr usage diagnostics (not the library's bare `incorrect usage`) and exit 2. Bare `./vrg` remains the help-only exception.
  6. `./vrg foo /nonexistent` exits 2; `./vrg foo -` exits 2 with a stdin-rejection message; `./vrg foo /dev/null` exits 2 on systems providing that special file.
  7. `./vrg foo ./go.mod` succeeds; roots that are symlinks to an existing directory or regular file also succeed.
  8. In a temporary directory containing a regular file named `-`, invoke the built binary with `foo ./-`; validation succeeds and exits 0.
  9. `./vrg "" .` succeeds with an empty pattern. `./vrg -- --help`, `./vrg -- -h`, `./vrg -- --`, and `./vrg - .` succeed with those literal patterns rather than showing help.
  10. An unsupported option such as `./vrg --unsupported` produces a sanitized stderr diagnostic naming the option and exits 2.
  11. Invoke the binary with a root operand containing an escape byte (e.g. `./vrg foo "$(printf '/no\033[31msuch')"`); the stderr diagnostic shows an escaped form and no raw control byte reaches the terminal.
- **Automated**:
  - CLI tests cover help-only results for no arguments and every help spelling before `--`: first-token `-h`/`--help`, later-token help (`foo --help /nonexistent`, `foo bar baz --help`, `--unsupported --help`), flag-preceded help without a pattern (`-i --help`), and combined help (`-ih`) — each with failing sentinels proving root validation, child startup, and TUI initialization never run on any help-only case, and help-like operands after `--` staying positional. Generated help content (syntax line, `PATTERN`, `ROOT` with `.` default, `-h`/`--help`) is asserted, as is the distinction between the library's first-token interception (`Run` returns `nil`, `Action` skipped — never relied on, because the preflight resolves help first) and a successful parse with a set local help value, which does invoke `Action` and must still produce the help-only result before any root validation or search work.
  - Table tests cover the default root, directory/regular-file/symlink roots, stdin and special-file rejection, nonexistent roots, arity errors outside help-only paths, the `./-` regular-file root, a present empty pattern, the literal `-` pattern, `--` positional handling (including help-like and literal `--` operands), and unsupported options. Each error case asserts the classified diagnostic kind, not the library's generic message.
  - Output tests cover hostile operand and executable-name substitutions in help, parser errors, root diagnostics, and the success stub. Assert external data cannot emit raw terminal controls or unescaped invalid bytes; legitimate help line breaks remain readable. Assert the CLI module writes help to the supplied writer, that exactly one help copy reaches stdout, and that nothing reaches the process stderr on the help path. Library-generated failures are covered, not only failures caught by root validation: for every usage error, including those detected by the library's parser, the raw stderr contains only the module's classified sanitized diagnostic — no library `Error:` line, no library help text, and no duplicate diagnostic.
  - Subprocess tests execute the built entry point and assert stdout, stderr, and exit status for help, successful parsing, and usage errors, across first-token, later-token, and combined help, including help with a missing pattern (`-i --help`, `-ih`) and with excess operands (`foo bar baz --help`). Help works with no rg on `PATH`, emits no TUI/alternate-screen sequences or stub output, and does not invoke a sentinel fake rg when one is available; every help-only case exits 0 with exactly one help copy on stdout and empty stderr. Test the entry-point dispatch boundary to verify that help never invokes TUI initialization and that exit codes are chosen by `cmd/vrg`, not by the library.

### Acceptance criteria

- [ ] Given a clean checkout and the approved Go toolchain, when the project is built, then `cmd/vrg` produces a runnable executable using pinned `github.com/jawher/mow.cli v1.2.0` for CLI parsing and help, not merely listing it as an unused dependency.
- [ ] Given the library integration, then `ErrorHandling` is `flag.ContinueOnError` and every exit status is chosen by the entry point; the library never calls `os.Exit`.
- [ ] Given no command-line arguments or local `-h`/`--help` anywhere before `--` — including invocations that would otherwise be missing-pattern, excess-operand, unsupported-option, or invalid-root usage errors — when the executable runs, then exactly one help copy goes to stdout and it exits 0 with empty stderr, without root validation, ripgrep startup, TUI initialization, or success-stub output.
- [ ] Given any invocation — help-only, usage error, or valid search — the library's native emissions (first-token help, parse-failure `Error:` text and help) never reach the process stderr; stdout carries exactly one sanitized help copy on help-only paths, and every usage error produces exactly the module's classified sanitized diagnostic on stderr.
- [ ] Given ripgrep is unavailable or a supplied root is invalid, when command-line help is requested, then help still succeeds without validating search prerequisites.
- [ ] Given generated help, then it describes syntax, the required pattern, the optional root and its `.` default, and local help options; Issue 2 extends it with the supported search flags without changing the emission path.
- [ ] Given `vrg pattern`, when the CLI parses, then root defaults to `.`.
- [ ] Given `vrg pattern root` where `root` is an existing directory or regular file, directly or via symlink, then validation succeeds.
- [ ] Given a non-help invocation missing a pattern, more than two positionals, or an unsupported option, then a sanitized single-line usage diagnostic identifying the failure kind is written to stderr and the process exits 2 without starting a child or TUI.
- [ ] Given `--`, then subsequent tokens are positionals, including `-h`, `--help`, and `--`, rather than local help requests or additional option terminators.
- [ ] Given a root of `-`, a special file, or a nonexistent path, then the process exits 2 with a sanitized diagnostic naming the reason.
- [ ] Given external data containing dangerous controls or invalid bytes, then CLI help, diagnostics, and the stub escape that data rather than emitting it raw, including any text the library renders.
- [ ] Given a root of `./-` naming an actual regular file called `-`, then validation succeeds.
- [ ] Given a present but empty pattern argument or a literal `-` pattern, then it is retained as a present positional and parsing succeeds.
- [ ] Given the CLI module's public result type, then help-only, parsed-search, and usage-error outcomes are distinct values; callers do not inspect library errors or strings to tell them apart.

### Definition of done

- [ ] The human decision above is resolved: the reviewer's approval of module path, package layout, Go version, pinned `mow.cli` / Bubble Tea / Bubbles / Lip Gloss versions, and the output strategy — proven to cover every library emission point — is recorded before merge.
- [ ] Build, CLI tests, and executable-boundary tests pass; the default-help path is demoable independently of Issue 2 and without ripgrep installed.
- [ ] Issue 2 can add allow-listed search flags as rows in the shared option-declaration table and declarations on the same `mow.cli` app — with the preflight scan recording their encounter order — without changing the spec shape, help emission, help-only precedence, or exit handling established here.

- User story 3: default/explicit help exits 0; invocation mistakes produce stderr diagnostics and exit 2 (search-flag-specific validation follows in Issue 2)
- User story 6 (parsing boundary only): `--` protects dash-leading positionals; child-argv protection follows in Issue 2
